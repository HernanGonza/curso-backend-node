CRUD en Memoria

Integrá todo lo aprendido en el Bloque 4: implementá las 4 operaciones CRUD completas usando un array en memoria, con validación robusta y respuestas JSON consistentes. El mismo patrón que usarás con PostgreSQL en el Bloque 6.

60 minutos Requiere Clase 18
Objetivos de la clase
  • Entender el patrón CRUD y su mapeo a los métodos HTTP.
  • Validar el body del request acumulando todos los errores.
  • Implementar Create, Read, Update y Delete con un array en memoria.
  • Usar el spread operator para actualizar objetos sin mutación.
  • Diseñar respuestas de error consistentes y seguras.

01CRUD — Las 4 Operaciones Fundamentales

Toda aplicación que maneja datos necesita poder hacer cuatro operaciones sobre ellos: crear registros nuevos, leer registros existentes, modificar registros, y eliminarlos. Estas cuatro operaciones tienen un acrónimo: CRUD (Create, Read, Update, Delete). Es un concepto tan fundamental que se aplica a cualquier sistema de gestión de datos: bases de datos SQL, APIs REST, sistemas de archivos, y más.

En una API REST, el CRUD mapea directamente a los métodos HTTP. Esta correspondencia no es arbitraria: cada método tiene una semántica específica. Un cliente que conoce REST sabe que para crear algo debe usar POST, para leer debe usar GET, para actualizar debe usar PUT, y para eliminar debe usar DELETE.

02Parsear y Validar el Body

Antes de crear o actualizar un recurso, es imprescindible validar los datos que llegaron en el body del request. La validación es la primera línea de defensa de tu API. Si no validás, podrías insertar datos corruptos en la base de datos (un email sin @, un nombre vacío), o ser víctima de ataques.

El patrón recomendado es acumular todos los errores de validación en un array y devolverlos todos juntos. Si el nombre es incorrecto Y el email también, el cliente recibe los dos errores al mismo tiempo y puede corregirlos juntos. Validar uno por uno y parar al primer error obliga al usuario a corregir y reenviar múltiples veces.

javascript
function validarUsuario(datos) {
  const errores = []; // acumulamos todos los errores juntos

  // Validacion del nombre:
  if (!datos.nombre || datos.nombre.trim() === '')
    errores.push('El nombre es obligatorio');

  // Validacion del email:
  if (!datos.email || !datos.email.includes('@'))
    errores.push('El email es invalido (debe contener @)');

  // Validacion de la contrasena:
  if (!datos.password || datos.password.length < 6)
    errores.push('La password debe tener al menos 6 caracteres');

  return errores; // array vacio = sin errores
}

// Uso en el endpoint POST:
const errores = validarUsuario(body);
if (errores.length > 0) {
  json(res, 400, { ok: false, errores });
  return; // early return - no continuar
}

03CRUD Completo en Memoria

Antes de conectar una base de datos real (Bloque 6 con PostgreSQL), implementar el CRUD con un array en memoria es una práctica excelente. Permite entender la lógica de cada operación sin la complejidad adicional del SQL ni la configuración de la base de datos. El comportamiento es idéntico: creás, leés, actualizás y eliminás. La única diferencia es que los datos se pierden al reiniciar el servidor.

Para el auto-incremento del ID usamos una variable nextId que incrementamos manualmente. Para leer por ID usamos findIndex() que nos da la posición en el array (necesaria para actualizar y eliminar). Para eliminar usamos filter() que devuelve un nuevo array sin el elemento, en lugar de splice() que mutaría el array original.

javascript
let usuarios = [
  { id: 1, nombre: 'Ana Garcia',  email: 'ana@mail.com'   },
  { id: 2, nombre: 'Bruno Lopez', email: 'bruno@mail.com' },
];
let nextId = 3; // simula el auto-increment de la BD

const servidor = http.createServer(async (req, res) => {
  const { pathname } = new URL(req.url, 'http://localhost');
  const method = req.method;

  // POST /api/usuarios - crear
  if (method === 'POST' && pathname === '/api/usuarios') {
    try {
      const body    = await leerBody(req);
      const errores = validarUsuario(body);
      if (errores.length) { json(res, 400, { ok: false, errores }); return; }
      const nuevo = { id: nextId++, nombre: body.nombre, email: body.email };
      usuarios.push(nuevo);
      json(res, 201, { ok: true, data: nuevo });
    } catch (e) { json(res, 400, { ok: false, error: e.message }); }
    return;
  }

  // GET /api/usuarios - listar todos
  if (method === 'GET' && pathname === '/api/usuarios') {
    json(res, 200, { ok: true, data: usuarios, total: usuarios.length });
    return;
  }

  // Rutas con ID
  const match = pathname.match(/^\/api\/usuarios\/(\d+)$/);
  if (!match) { json(res, 404, { ok: false, error: 'Ruta no encontrada' }); return; }

  const id  = parseInt(match[1]);
  const idx = usuarios.findIndex(u => u.id === id);

  if (method === 'GET') {
    if (idx < 0) { json(res, 404, { error: `Usuario ${id} no encontrado` }); return; }
    json(res, 200, { data: usuarios[idx] });

  } else if (method === 'PUT') {
    if (idx < 0) { json(res, 404, { error: 'No encontrado' }); return; }
    const body = await leerBody(req);
    usuarios[idx] = { ...usuarios[idx], ...body, id }; // spread para actualizar
    json(res, 200, { data: usuarios[idx] });

  } else if (method === 'DELETE') {
    if (idx < 0) { json(res, 404, { error: 'No encontrado' }); return; }
    usuarios = usuarios.filter(u => u.id !== id);
    res.writeHead(204); res.end(); // 204: exito sin cuerpo
  }
});

04Actualizar sin Mutar — El Spread Operator

Para la operación Update (PUT) necesitamos actualizar los campos que el cliente envió, pero conservar los que no envió. Si un usuario tiene { id, nombre, email, activo, createdAt } y el cliente solo envía { nombre: 'nuevo nombre' }, queremos actualizar solo el nombre y dejar el resto intacto.

La forma correcta es usar el spread operator (...) para crear un objeto nuevo que combine el original con los cambios. Los cambios sobreescriben los campos del original con el mismo nombre, y los campos del original que no están en cambios se conservan. Siempre se pone el id al final para garantizar que no pueda ser sobreescrito por los datos del body.

javascript
const original = { id: 1, nombre: 'Ana', email: 'ana@mail.com', activo: true };
const cambios  = { nombre: 'Ana Garcia', email: 'ana.garcia@mail.com' };

// Spread: copia el original y aplica los cambios encima
const actualizado = { ...original, ...cambios, id: 1 };

console.log(actualizado);
// { id: 1, nombre: 'Ana Garcia', email: 'ana.garcia@mail.com', activo: true }
// El campo 'activo' se mantuvo aunque no estaba en los cambios.
// El id al final garantiza que nadie pueda cambiar el ID del recurso.

05Respuestas de Error Consistentes

Una API de calidad profesional no solo funciona cuando todo va bien: también falla de forma predecible y descriptiva. El cliente necesita poder manejar los errores de forma automática. Para eso, todos los errores deben tener la misma estructura: si a veces el error viene en error.mensaje y otras en data.errorMsg, el cliente tiene que escribir código especial para cada caso.

Un detalle de seguridad importante: los errores internos del servidor nunca deben revelar detalles de implementación (como mensajes de error de la base de datos o nombres de tablas) porque esa información ayuda a atacantes. El mensaje que ve el cliente debe ser genérico; el detalle completo se registra solo en los logs del servidor.

javascript
// Estructura estandar de respuestas:
// Exito:  { ok: true,  data: ..., total: ... }
// Error:  { ok: false, error: '...', errores: [...] }

// 400 - datos invalidos:
{ ok: false, errores: ['Nombre obligatorio', 'Email invalido'] }

// 404 - no encontrado:
{ ok: false, error: 'Usuario con ID 99 no encontrado' }

// 500 - error interno (mensaje generico por seguridad):
{ ok: false, error: 'Error interno del servidor' }

// La funcion manejadora de errores internos:
try {
  // codigo que puede fallar...
} catch (error) {
  console.error('Error interno:', error); // log completo para el dev
  json(res, 500, { ok: false, error: 'Error interno del servidor' });
}
