Servidor con Express

Profundizá en app.listen(), aprendé a organizar un proyecto Express en carpetas a medida que crece, y automatizá el reinicio del servidor durante el desarrollo con nodemon.

60 minutos Requiere Clase 20
Objetivos de la clase

  • Escribir un callback de confirmación de arranque siguiendo buenas prácticas profesionales.
  • Organizar un proyecto Express en carpetas a medida que el código crece, anticipando el patrón routes/controllers.
  • Distinguir dependencies de devDependencies y entender el rol de los scripts en package.json.
  • Identificar el problema que resuelve nodemon e instalarlo correctamente en un proyecto real.

01app.listen(): Poniendo el Servidor a Escuchar

Hasta ahora vimos cómo Express permite definir rutas con app.get() y devolver respuestas con res.json(). Pero ninguna de esas rutas puede recibir tráfico real hasta que el servidor esté efectivamente escuchando en un puerto de la máquina. Esa es la responsabilidad exclusiva de app.listen(): le indica al sistema operativo "reservá este puerto y avisame cada vez que llegue una conexión entrante".

Un puerto es, conceptualmente, una puerta numerada dentro de una misma dirección IP. Una computadora puede tener decenas de programas escuchando simultáneamente, y el puerto es lo que le permite al sistema operativo saber a cuál de ellos entregarle cada paquete de red que llega. Cuando escribís http://localhost:3000 en el navegador, el 3000 le dice exactamente a qué proceso tiene que llegar ese pedido.

💡
Analogía práctica: Pensá en un edificio de oficinas (la máquina) con muchas puertas numeradas (los puertos). app.listen(3000) es como colgar un cartel en la puerta 3000 que dice «acá atiende la aplicación de la tienda virtual». Si nadie cuelga ese cartel, cualquiera que golpee esa puerta no encuentra a nadie del otro lado.
javascript
const express = require('express');
const app = express();

app.get('/', (req, res) => {
  res.json({ mensaje: 'Servidor funcionando' });
});

app.listen(3000); // El servidor queda escuchando en el puerto 3000

Es importante notar que app.listen() es, generalmente, la última línea del archivo principal del servidor. Todo lo que se define antes (rutas, middlewares, configuración) se registra en memoria primero; recién cuando se llama a listen() el servidor arranca a procesar conexiones reales.

02El Callback de Confirmación de Arranque

app.listen() acepta un segundo parámetro opcional: una función callback que se ejecuta apenas el servidor termina de inicializarse y queda listo para recibir tráfico. En un entorno profesional, este callback nunca se omite: es la única forma de tener una confirmación explícita en la consola de que todo arrancó correctamente.

javascript
const PORT = 3000;

app.listen(PORT, () => {
  console.log(`Servidor corriendo en http://localhost:${PORT}`);
});
⚠️
Error común de principiante: Escribir código después de app.listen() esperando que se ejecute «antes» del arranque. app.listen() no bloquea el archivo: Node.js sigue leyendo lo que sigue debajo de inmediato. Toda lógica que dependa de que el servidor ya esté arriba tiene que ir dentro del callback, nunca después de la llamada.

Buenas prácticas al centralizar el puerto

En vez de escribir el número de puerto "hardcodeado" en el medio del archivo, es una convención profesional definirlo como una constante al principio, y más adelante (Bloque 6) tomarlo de una variable de entorno con process.env.PORT. Por ahora, alcanza con declararlo como una constante clara y reutilizable.

03Estructura de un Proyecto Express en Crecimiento

Cuando un servidor Express tiene solo dos o tres rutas, tenerlas todas en un único archivo index.js no genera ningún problema. Pero a medida que el proyecto crece —nuevas entidades, nueva lógica de negocio, nuevas validaciones— ese archivo único se vuelve inmanejable: cientos de líneas mezclando configuración del servidor, rutas y lógica de negocio.

La solución no es técnica sino organizativa: separar responsabilidades en carpetas y archivos con un propósito claro y único. Esta es una convención ampliamente adoptada en la comunidad de Node.js y Express, y es la que vas a encontrar en casi cualquier proyecto backend profesional.

Carpeta / ArchivoResponsabilidad
index.jsPunto de entrada. Crea la app, registra middlewares globales y llama a app.listen().
routes/Define qué URLs existen y a qué función responden. No contiene lógica de negocio.
controllers/Contiene la lógica de negocio real: qué hacer cuando llega cada request.
models/Representa los datos de la aplicación (más adelante, conectado a la base de datos).
node_modules/Carpeta autogenerada con las dependencias instaladas. Nunca se edita ni se sube a git.
🛡️
Por qué importa: Separar en carpetas no es una moda estética: permite que varias personas trabajen en el mismo proyecto sin pisarse, facilita encontrar dónde está cada cosa, y hace que el código sea testeable en partes aisladas. En la Clase 22 vamos a poner esta estructura en práctica de forma concreta con rutas y controllers reales.

04package.json: Scripts y Dependencias

El archivo package.json es el documento central de cualquier proyecto Node.js: describe el nombre del proyecto, su versión, y sobre todo, qué paquetes externos necesita para funcionar y qué comandos personalizados están disponibles para ejecutarlo.

json
{
  "name": "tienda-virtual-api",
  "version": "1.0.0",
  "scripts": {
    "start": "node index.js",
    "dev": "nodemon index.js"
  },
  "dependencies": {
    "express": "^4.19.2"
  },
  "devDependencies": {
    "nodemon": "^3.1.0"
  }
}
CampoQué representa
dependenciesPaquetes necesarios para que la aplicación funcione en producción (ej: express).
devDependenciesPaquetes usados únicamente durante el desarrollo, no en producción (ej: nodemon).
scriptsAtajos de terminal. Se ejecutan con npm run <nombre> (excepto "start", que usa solo npm start).

La diferencia entre dependencies y devDependencies se define al momento de instalar el paquete: npm install express lo agrega como dependencia de producción, mientras que npm install nodemon --save-dev (o su forma corta -D) lo agrega como dependencia de desarrollo.

05El Problema que Resuelve Nodemon

Node.js, por diseño, ejecuta un archivo de principio a fin y no vuelve a leerlo automáticamente si el código cambia. Esto significa que, durante el desarrollo, cada vez que modificás y guardás una ruta, tenés que ir manualmente a la terminal, frenar el proceso con Ctrl+C, y volver a ejecutar node index.js para ver el cambio reflejado. Repetir esto decenas de veces por hora es lento y rompe el flujo de trabajo.

💡
Analogía práctica: Es como si cada vez que corregis una palabra en un documento tuvieras que cerrar el programa entero y volver a abrirlo para ver la corrección. Nodemon automatiza exactamente esa recarga.

Nodemon ("Node Monitor") es una herramienta que envuelve la ejecución de Node.js y observa constantemente los archivos del proyecto. Apenas detecta que alguno cambió y fue guardado, reinicia el servidor automáticamente, sin intervención manual.

06Instalar y Configurar Nodemon

Nodemon se instala como dependencia de desarrollo, ya que es una herramienta exclusiva del entorno local de programación: nunca se necesita en el servidor real donde corre la aplicación en producción.

bash
npm install nodemon --save-dev

# Alternativa instalandolo de forma global en la maquina (no recomendado por proyecto):
# npm install -g nodemon

Una vez instalado, se agrega el script "dev": "nodemon index.js" dentro de package.json (como se mostró en la sección anterior), y a partir de ahí el flujo de trabajo diario pasa a ser el siguiente:

bash
npm run dev

[nodemon] starting `node index.js`
Servidor corriendo en http://localhost:3000
[nodemon] restarting due to changes...   # se reinicia solo al guardar un archivo
⚠️
Importante: npm start sigue funcionando igual que siempre con node index.js —es el comando estándar que se usa en producción—. npm run dev es exclusivamente para el día a día de desarrollo local, con recarga automática.
