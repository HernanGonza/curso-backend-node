Request y Response

Explorá en profundidad los dos objetos más importantes de cualquier servidor: el request con toda la información del cliente (URL, método, headers, body) y la response con las herramientas para construir respuestas JSON correctas.

60 minutos Requiere Clase 16
Objetivos de la clase
  • Inspeccionar en profundidad el objeto req: URL, método y headers.
  • Parsear query strings con el constructor URL nativo.
  • Construir respuestas JSON correctas con el Content-Type adecuado.
  • Entender por qué el body llega como stream y cómo leerlo correctamente.
  • Conocer los status codes HTTP más importantes y cuándo usarlos.

01El Objeto req — Toda la Información del Cliente

En la clase anterior creamos un servidor que responde siempre lo mismo. Pero un servidor real necesita saber qué le está pidiendo el cliente para dar la respuesta correcta. Toda esa información vive en el objeto req.

req.url contiene la ruta que solicitó el cliente, incluyendo el query string (los parámetros que van después del signo ?). Por ejemplo, para un request a /api/usuarios?pagina=2&limite=10, el valor de req.url es exactamente ese string completo.

req.method contiene el método HTTP del request, siempre en mayúsculas. Es lo que diferencia si el cliente quiere obtener datos (GET), crear un recurso (POST), actualizarlo (PUT) o eliminarlo (DELETE).

req.headers es un objeto con todos los headers que el cliente envió: el Content-Type dice qué formato tiene el body, el Authorization lleva el token de autenticación, el User-Agent identifica qué cliente está haciendo el pedido. En Node.js, todos los nombres de headers se convierten a minúsculas automáticamente.

javascript
const servidor = http.createServer((req, res) => {

  console.log('URL completa:', req.url);
  // Ej: '/api/usuarios?pagina=2&limite=10'

  console.log('Metodo:', req.method);
  // Posibles: 'GET', 'POST', 'PUT', 'PATCH', 'DELETE'

  console.log('Todos los headers:', req.headers);
  console.log('Content-Type:',  req.headers['content-type']);
  console.log('Authorization:', req.headers['authorization']);
  console.log('User-Agent:',    req.headers['user-agent']);

  res.end('Request recibido');
});

02Parsear la URL y los Query Strings

La propiedad req.url devuelve la URL como un string completo. Si la URL tiene query string (parámetros después del ?), necesitamos parsearla para acceder a cada parámetro individualmente. No podemos hacerlo con split() de forma confiable, porque los valores pueden contener caracteres especiales (espacios codificados como %20, por ejemplo).

La solución es usar el constructor new URL(), que parsea la URL en todas sus partes: el pathname (el camino sin los parámetros) y el objeto searchParams que permite acceder a cada parámetro por nombre con el método .get(). Un detalle importante: searchParams.get() siempre devuelve un string o null. Si el parámetro es un número, hay que convertirlo con parseInt().

javascript
// Request entrante: GET /api/usuarios?pagina=2&limite=10&buscar=ana

const servidor = http.createServer((req, res) => {

  const urlObj = new URL(req.url, 'http://localhost');

  console.log(urlObj.pathname);                       // '/api/usuarios'
  console.log(urlObj.searchParams.get('pagina'));     // '2' (siempre string)
  console.log(urlObj.searchParams.get('limite'));     // '10'
  console.log(urlObj.searchParams.get('buscar'));     // 'ana'
  console.log(urlObj.searchParams.get('orden'));      // null (no existe)

  // Convertir a numero con fallback para evitar NaN:
  const pagina = parseInt(urlObj.searchParams.get('pagina')) || 2;
  const limite = parseInt(urlObj.searchParams.get('limite')) || 10;

  res.end(`Pagina ${pagina}, ${limite} resultados`);
});

03Enviar JSON como Respuesta

Toda API REST responde principalmente con JSON (JavaScript Object Notation). Para que el cliente pueda interpretar correctamente la respuesta, es obligatorio declarar dos cosas: el status code y el header Content-Type: application/json. Sin ese header, el cliente no sabe que el cuerpo es JSON y puede no procesarlo correctamente.

El proceso siempre es el mismo: llamar a res.writeHead() con el status y el header, y luego res.end() con el resultado de JSON.stringify(objeto). Como este proceso se repite en cada endpoint, la buena práctica es extraerlo en una función helper enviarJSON(). Así si necesitás cambiar algo (agregar un header CORS), lo cambiás en un solo lugar.

javascript
// Funcion helper reutilizable - la usas en TODOS tus endpoints:
function enviarJSON(res, statusCode, datos) {
  res.writeHead(statusCode, {
    'Content-Type': 'application/json; charset=utf-8',
    'Access-Control-Allow-Origin': '*',
  });
  res.end(JSON.stringify(datos));
}

const servidor = http.createServer((req, res) => {
  if (req.url === '/api/usuarios' && req.method === 'GET') {
    const usuarios = [
      { id: 1, nombre: 'Ana Garcia',  email: 'ana@mail.com'   },
      { id: 2, nombre: 'Bruno Lopez', email: 'bruno@mail.com' },
    ];
    // Estructura consistente: siempre con ok:true y data:
    enviarJSON(res, 200, { ok: true, data: usuarios, total: usuarios.length });
  } else {
    enviarJSON(res, 404, { ok: false, error: 'Ruta no encontrada' });
  }
});

04Leer el Body de un POST — Streams

A diferencia de la URL y los headers (que llegan completamente en el primer paquete del request), el body de un request POST o PUT llega como un stream de datos. ¿Por qué? Porque HTTP no garantiza que todos los datos lleguen juntos en un solo paquete de red. Un body puede ser un JSON de 50 bytes (llega todo junto en la práctica) o un archivo de 50MB (llega en decenas de fragmentos).

Node.js notifica la llegada de datos usando eventos. El evento 'data' se dispara cada vez que llega un fragmento del body. El evento 'end' se dispara cuando llegaron absolutamente todos los fragmentos y el body está completo. Solo en ese momento podemos parsear el JSON con seguridad.

La función leerBody() encapsula este patrón en una Promesa para poder usarla con async/await. Incluye una protección importante: si el body supera los 10KB, lo rechaza inmediatamente para prevenir ataques donde un cliente malicioso envía un body enorme para agotar la memoria del servidor.

javascript
function leerBody(req) {
  return new Promise((resolve, reject) => {
    let body = '';

    // 'data' se dispara cada vez que llega un fragmento:
    req.on('data', (chunk) => {
      body += chunk.toString();
      // Proteccion: rechazar bodies mayores a 10KB
      if (body.length > 10240) {
        reject(new Error('Body demasiado grande'));
        req.destroy();
      }
    });

    // 'end' se dispara cuando llegaron TODOS los fragmentos:
    req.on('end', () => {
      try { resolve(JSON.parse(body)); }
      catch (e) { reject(new Error('JSON invalido en el body')); }
    });

    req.on('error', reject);
  });
}

// Uso en un endpoint POST:
const servidor = http.createServer(async (req, res) => {
  if (req.method === 'POST' && req.url === '/api/usuarios') {
    try {
      const datos = await leerBody(req);
      console.log('Datos recibidos:', datos);
      enviarJSON(res, 201, { ok: true, datos });
    } catch (error) {
      enviarJSON(res, 400, { ok: false, error: error.message });
    }
  }
});

05Status Codes — El Vocabulario del HTTP

Los códigos de status HTTP son números de tres dígitos que el servidor incluye en cada respuesta para comunicarle al cliente si la operación fue exitosa o si hubo algún problema. Son parte del estándar HTTP y tienen significados universales. Usar los códigos incorrectos (por ejemplo, responder 200 cuando hubo un error) es un error de diseño serio que confunde a los clientes de la API.

Los códigos se agrupan por familias: los 2xx indican éxito, los 4xx indican errores del cliente (el cliente hizo algo mal), y los 5xx indican errores del servidor. La distinción entre 4xx y 5xx es crucial para depurar: un 4xx significa que el cliente envió datos incorrectos; un 5xx significa que hay un bug en el servidor.
