Empezamos el Bloque 4. Descubrí el entorno que hace posible JavaScript en el servidor: módulos nativos para el sistema de archivos, rutas y sistema operativo, la diferencia entre CommonJS y ES Modules, cómo crear módulos propios y cómo gestionar dependencias con npm.

01¿Qué es Node.js?

Antes de Node.js, JavaScript era exclusivo del navegador. No había forma de ejecutarlo en un servidor para manejar rutas, conectarse a bases de datos o leer archivos del disco. Cada lenguaje de backend (PHP, Ruby, Java, Python) era completamente distinto, lo que obligaba a aprender dos lenguajes diferentes para construir una sola aplicación web.

En 2009, Ryan Dahl tomó el motor V8 —el motor de JavaScript de Google Chrome— y lo integró en un programa que podía correr directamente en el sistema operativo, fuera del navegador. A ese entorno lo llamó Node.js. Es un entorno de ejecución, no un framework ni una librería: una capa que permite que el motor V8 funcione en el servidor y que provee acceso al sistema operativo (leer archivos, crear servidores de red, ejecutar procesos del sistema).

💡
¿Por qué Node.js para backend? Heredó el Event Loop no-bloqueante del navegador (Clase 12). Puede manejar miles de solicitudes simultáneas con un solo hilo: en lugar de esperar bloqueado a que la base de datos responda, registra un callback y atiende otras solicitudes mientras tanto.

02Módulo fs — Sistema de Archivos

Cuando un servidor necesita leer archivos de configuración, guardar logs de errores, o procesar archivos subidos por usuarios, necesita acceder al sistema de archivos del servidor. El módulo nativo fs (file system) provee todas las funciones para interactuar con archivos y directorios. Es parte del núcleo de Node.js, no requiere instalación con npm.

Una decisión de diseño clave: casi todas las operaciones de fs son asíncronas por defecto. Leer un archivo puede tardar milisegundos dependiendo del tamaño. Si fuera bloqueante, el servidor quedaría congelado atendiendo a un solo usuario mientras lee. El módulo tiene dos formas de uso: la antigua con callbacks, y la moderna con Promesas (recomendada con async/await).

javascript
const fs = require('fs');

// FORMA ANTIGUA: callbacks
fs.readFile('config.json', 'utf8', (error, contenido) => {
  if (error) { console.log('Error:', error.message); return; }
  console.log('Contenido:', contenido);
});

fs.writeFile('log.txt', 'Servidor iniciado: ' + new Date(), (error) => {
  if (!error) console.log('Log guardado OK');
});

// FORMA MODERNA: Promesas con async/await (recomendada)
const fsP = require('fs').promises;

async function leerConfig() {
  try {
    const texto = await fsP.readFile('config.json', 'utf8');
    return JSON.parse(texto);
  } catch (e) {
    return { puerto: 3000 }; // defaults si el archivo no existe
  }
}

async function guardarDatos(datos) {
  const contenido = JSON.stringify(datos, null, 2);
  await fsP.writeFile('datos.json', contenido, 'utf8');
  console.log('Datos guardados');
}

03Módulo path — Rutas de Archivos Seguras

Un problema clásico al trabajar con archivos en el servidor es construir las rutas correctamente. En Linux/Mac, las rutas usan barra inclinada: /home/usuario/proyecto/data. En Windows, usan barra invertida. Si concatés strings manualmente para armar rutas, tu servidor puede funcionar en desarrollo pero fallar en producción si los entornos usan sistemas operativos distintos.

El módulo path resuelve esto: construye rutas de forma agnóstica al SO, detectando automáticamente el separador correcto. Además, Node.js inyecta automáticamente __dirname (directorio del archivo actual) y __filename (ruta completa del archivo) en cada archivo. Son fundamentales para construir rutas que siempre funcionen sin importar desde dónde se ejecute el proyecto.

javascript
const path = require('path');

// __dirname: ruta del directorio donde esta ESTE archivo
console.log(__dirname); // ej: '/home/usuario/mi-proyecto/src'

// path.join() construye rutas seguras sin importar el SO:
const ruta = path.join(__dirname, 'data', 'usuarios.json');
// -> '/home/usuario/mi-proyecto/src/data/usuarios.json'

// Extraer partes de una ruta existente:
const archivo = '/home/usuario/proyecto/servidor.js';
console.log(path.basename(archivo));        // 'servidor.js'
console.log(path.dirname(archivo));         // '/home/usuario/proyecto'
console.log(path.extname(archivo));         // '.js'
console.log(path.basename(archivo, '.js')); // 'servidor' (sin ext)

04Módulo os — Información del Sistema

El módulo os (operating system) provee información sobre el sistema operativo y el hardware donde corre el servidor. Es útil para construir endpoints de monitoreo (health checks), para tomar decisiones de configuración automática (crear tantos workers como núcleos de CPU tenga el servidor), o para registrar en logs qué entorno está corriendo la aplicación.

javascript
const os = require('os');

console.log(os.platform());    // 'linux', 'win32', 'darwin' (Mac)
console.log(os.arch());        // 'x64', 'arm64'
console.log(os.cpus().length); // cantidad de nucleos del CPU

const ramTotal = os.totalmem() / 1024 / 1024 / 1024;
const ramLibre = os.freemem()  / 1024 / 1024 / 1024;
console.log(`RAM: ${ramLibre.toFixed(1)}GB libres de ${ramTotal.toFixed(1)}GB`);

// Endpoint de salud del servidor:
function estadoServidor() {
  return {
    ok:      true,
    uptime:  process.uptime() + ' segundos',
    cpu:     os.cpus().length + ' nucleos',
    sistema: os.platform() + ' ' + os.arch(),
  };
}

05require vs import — Los Dos Sistemas de Módulos

Un sistema de módulos resuelve cómo dividir un programa grande en múltiples archivos y cómo hacer que se "vean" entre sí. JavaScript no tuvo un sistema nativo durante muchos años. En 2009, la comunidad de Node.js creó CommonJS con require y module.exports. En 2015, el estándar oficial incorporó ES Modules con import y export. Hoy coexisten los dos.

La diferencia práctica más importante: require() puede usarse en cualquier parte del código, incluso dentro de condiciones o funciones. El import estático solo puede ir al nivel superior del archivo.

SistemaSintaxisCaracterística clave
CommonJS (require)const x = require('modulo')Nativo de Node.js, sincrono, flexible
ES Modules (import)import x from 'modulo'Estándar moderno, estatico, nivel superior
💡
Para el curso: Usaremos require (CommonJS). Es el sistema que encontrarás en la documentación de Express y en la mayoría de proyectos reales. Una vez que lo domines, el salto a ES Modules es trivial.
javascript
// CommonJS (require) - el sistema nativo de Node.js:
const express = require('express');      // paquete npm
const http    = require('http');         // modulo nativo
const miUtil  = require('./utils/val');  // archivo propio (./ obligatorio)

// require() puede usarse condicionalmente:
if (process.env.DEBUG) {
  const logger = require('./debug-logger'); // OK - carga condicional
  // import logger from './debug-logger';  // ERROR - import es siempre estatico
}

06Módulos Propios — Organizar el Código

La modularización consiste en dividir el código en archivos pequeños con responsabilidad única. En lugar de un index.js de 2000 líneas que hace todo, cada responsabilidad se aísla: validaciones, lógica de negocio, acceso a datos. Los archivos pequeños son más fáciles de leer, de depurar y de trabajar en equipo.

En Node.js con CommonJS, cada archivo tiene su propio scope aislado: las variables declaradas en un archivo no se escapan al resto del programa. Para compartir funciones con otros archivos se usa module.exports. Para consumirlas se usa require('./ruta'). El ./ al inicio es obligatorio para archivos propios; sin él, Node.js busca en node_modules.

javascript
// archivo: utils/validaciones.js
function validarEmail(email) {
  if (!email || typeof email !== 'string') return false;
  return email.includes('@') && email.includes('.');
}
function validarPassword(password) {
  if (!password) return false;
  return password.length >= 6;
}
// Solo lo que ponemos en module.exports es visible desde afuera:
module.exports = { validarEmail, validarPassword };

// archivo: index.js
// El ./ le dice a Node.js que es un archivo local, no un paquete npm
const { validarEmail, validarPassword } = require('./utils/validaciones');

console.log(validarEmail('ana@mail.com')); // true
console.log(validarEmail('correo-roto'));  // false
console.log(validarPassword('abc'));       // false
console.log(validarPassword('segura123')); // true
✅
Convención de carpetas: routes/ para rutas, controllers/ para lógica, utils/ para auxiliares, models/ para datos. Esta organización la usaremos en el Bloque 5 con Express.

07npm y package.json — Gestión de Dependencias

npm (Node Package Manager) tiene más de dos millones de paquetes. Es el repositorio de código reutilizable más grande del mundo. Cuando necesitás autenticación con JWT, conectarte a PostgreSQL, enviar emails, o comprimir imágenes, casi siempre existe un paquete en npm que lo hace.

El archivo package.json es el corazón de cualquier proyecto Node.js: describe el nombre, versión, scripts y dependencias. Las dependencies son paquetes necesarios en producción (Express, bcrypt). Las devDependencies son herramientas solo para desarrollo (nodemon, jest) que no se instalan en el servidor de producción.

nodemon merece mención especial: vigila los archivos y reinicia el servidor automáticamente al detectar cambios. Sin nodemon, hay que hacer Ctrl+C y volver a ejecutar node index.js cada vez que se modifica una línea.

⚠️
node_modules y .gitignore: Nunca subas esta carpeta a Git. Puede pesar cientos de MB y contener miles de archivos. Agregála al .gitignore. Cualquier persona que clone el repositorio puede regenerarla con npm install.
bash
# Inicializar el proyecto (crea package.json):
npm init -y

# Instalar dependencias de produccion:
npm install express
npm install express pg dotenv bcrypt  # varias a la vez

# Instalar dependencias de DESARROLLO:
npm install --save-dev nodemon

# Instalar todo en un proyecto clonado de Git:
npm install
json
{
  "name": "backend-desde-cero",
  "version": "1.0.0",
  "scripts": {
    "start": "node index.js",    // para produccion
    "dev":   "nodemon index.js"  // para desarrollo
  },
  "dependencies":    { "express": "^4.18.2" },
  "devDependencies": { "nodemon": "^3.0.1" }
}
