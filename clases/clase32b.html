Bonus: Supabase y Alternativas

Una mirada rápida a las plataformas de Backend as a Service: qué es Supabase, qué resuelve automáticamente de lo que armamos a mano en el Proyecto Final, y qué otras opciones existen.

30 minutos Requiere Bloque 7 completo
Objetivos de la clase
  • Entender qué es Supabase y por qué se lo describe como un Backend as a Service (BaaS) construido sobre PostgreSQL.
  • Conocer sus funcionalidades principales: base de datos, API autogenerada, autenticación, storage y tiempo real.
  • Relacionar Supabase con lo aprendido en el curso: por debajo sigue siendo PostgreSQL y SQL relacional.
  • Conocer alternativas a Supabase (Turso, Convex, Neon, Railway, PlanetScale) y cuándo elegir cada una.
  • Identificar cuándo conviene usar un servicio como Supabase y cuándo conviene armar el backend a mano.

01¿Qué es Supabase?

Supabase es una plataforma de Backend as a Service (BaaS): en vez de programar un servidor Express desde cero como se hizo en el Proyecto Final, se usa una infraestructura ya lista, con una base de datos PostgreSQL real por debajo. En vez de escribir cada endpoint, cada conexión y cada validación a mano, todo eso viene resuelto de fábrica dentro de un mismo panel.

💡
Por qué importa que sea PostgreSQL: Todo lo aprendido sobre tablas, columnas, claves foráneas, JOIN y SQL sigue aplicando exactamente igual dentro de Supabase. No es tecnología nueva: es la misma base de datos relacional, con más herramientas alrededor.

02Para Qué Sirve: sus Funcionalidades Principales

Al crear un proyecto en Supabase, se obtiene de entrada un conjunto de servicios que en este curso se armaron a mano, clase por clase.

FuncionalidadQué resuelve
Base de datosUn PostgreSQL gestionado, con un editor visual de tablas parecido a Antares.
API REST autogeneradaAl crear una tabla, genera automáticamente endpoints GET/POST/PUT/DELETE, sin escribir routes ni controllers.
AutenticaciónSistema de usuarios listo: registro, login, recuperación de contraseña, login con Google o GitHub.
StorageEspacio para subir y servir archivos, similar a un bucket de Amazon S3.
RealtimeEl frontend recibe automáticamente los cambios de la base de datos en vivo.
🛡️
Esto es exactamente lo que armamos a mano: La API REST, el CRUD, y en parte la base de datos gestionada del Proyecto Final son justamente las piezas que Supabase ofrece ya empaquetadas de fábrica.

03Cómo se Conecta con lo que Ya Aprendiste

Trabajar con Supabase no reemplaza entender SQL: lo da por sentado. En vez de escribir pool.query() dentro de un service de Express (Clase 30), se puede usar el cliente oficial supabase-js, que arma esa misma consulta con menos código.

javascript
// Con Express + pg, como se armo en el Proyecto Final (Clase 30)
const resultado = await pool.query('SELECT * FROM productos WHERE id = $1', [id]);
const producto = resultado.rows[0];

// El mismo resultado usando el cliente de Supabase
const { data, error } = await supabase
  .from('productos')
  .select('*')
  .eq('id', id)
  .single();

Detrás de ambas líneas hay exactamente la misma tabla PostgreSQL, con las mismas columnas y las mismas reglas de integridad vistas en el Bloque 6.

04Alternativas a Supabase

Algunas alternativas siguen usando SQL relacional por debajo (Turso, Neon, PlanetScale), mientras que otras adoptan un modelo distinto, como Convex, con su propia base de datos de documentos reactiva en vez de tablas SQL.

ServicioQué ofreceCuándo conviene
TursoBase de datos SQLite distribuida (libSQL), replicada cerca del usuario en distintas regiones.Proyectos livianos con lecturas muy frecuentes desde varias regiones, o apps en el edge.
ConvexBackend reactivo: base de documentos, funciones serverless y sincronización en tiempo real, todo en TypeScript.Apps con mucho estado en vivo (dashboards colaborativos, chats) sin armar WebSockets a mano.
NeonPostgreSQL serverless, con "branching" de bases de datos para testing.Cuando solo hace falta la base de datos gestionada, sin auth ni storage.
RailwayHosting simple para bases de datos y backends propios, similar a Render.Deployar un backend hecho a mano, como el Proyecto Final de este curso.
PlanetScaleBase de datos MySQL serverless, también con branching.Proyectos que ya usan MySQL en vez de PostgreSQL.
⚠️
Ojo con Convex: A diferencia de Supabase, Turso o Neon, Convex no usa SQL: los datos se consultan y modifican con funciones de TypeScript. Es una forma distinta de pensar el backend, con tipado fuerte end-to-end.

05¿Cuándo Conviene Usar Supabase y Cuándo Armar el Backend a Mano?

Ninguna de las dos opciones es "mejor" en absoluto: depende de qué necesita el proyecto.

💡
Un servicio como Supabase, Turso o Convex conviene para: Prototipos rápidos, MVPs, proyectos personales o de portfolio donde se quiere ahorrar el tiempo de configurar auth, storage y un CRUD básico desde cero.
🛡️
Armar el backend a mano conviene para: Proyectos con lógica de negocio compleja, validaciones particulares, o cuando se necesita control total sobre cada endpoint.

En los caminos basados en SQL (Supabase, Turso, Neon, PlanetScale) sigue aplicando todo lo aprendido sobre tablas y relaciones. En Convex, en cambio, esa base se traslada a pensar el modelo de datos como funciones de TypeScript en vez de sentencias SQL.
