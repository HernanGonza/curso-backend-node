01Una App Real No es una Sola Cosa

Cuando usás Instagram, YouTube o Mercado Libre, no estás hablando con un solo programa. Hay tres partes bien diferenciadas trabajando juntas todo el tiempo.

Frontend Backend (API) Base de Datos
La pantalla que vesEl cerebro de la appLa memoria permanente
React, HTML, CSS, apps móvilesNode.js, Python, Java, etc.PostgreSQL, MySQL, MongoDB
Corre en el dispositivo del usuarioCorre en el servidor (la nube)Corre en el servidor, guarda todo
Habla con el backend via HTTPRecibe requests, procesa, respondeEl backend le hace consultas (SQL)
🍽️
Analogía del restaurante: La API es como el menú — lista todo lo que podés pedir (endpoints), cómo pedirlo (método HTTP + datos requeridos) y qué te van a traer (formato de la respuesta). No necesitás saber cómo se cocina — solo usás el menú.

02Qué es una API

API significa Application Programming Interface — interfaz de programación de aplicaciones. Es el conjunto de reglas que define cómo el frontend puede hablar con el backend: qué URLs existen, qué datos se mandan y qué datos se reciben.

El estilo de diseño que usa métodos HTTP + URLs claras para representar acciones sobre recursos se llama REST (Representational State Transfer). Es el estándar más usado en el mundo para construir backends. Durante todo el curso vamos a construir APIs REST.

Ejemplo: endpoints de una app de tareas (To-Do)

MétodoURL (endpoint)Qué hace
GET/api/tareasDevuelve la lista de todas las tareas
GET/api/tareas/5Devuelve solo la tarea con id 5
POST/api/tareasCrea una tarea nueva (manda datos en el body)
PUT/api/tareas/5Reemplaza completamente la tarea 5
PATCH/api/tareas/5Marca la tarea 5 como completada
DELETE/api/tareas/5Elimina la tarea 5

03El Ciclo Completo: del Clic a la Base de Datos

Vamos a seguir paso a paso lo que pasa cuando un usuario inicia sesión en una app real. Es el ejemplo más común y el que mejor ilustra cómo trabajan las tres capas juntas.

Escenario: el usuario hace clic en "Iniciar Sesión"

1
El usuario completa el formulario. El frontend (React, HTML, app móvil) recolecta el email y la password. El usuario hace clic en el botón.
2
El frontend envía un HTTP Request al backend. Se arma y envía un POST a /api/login con los datos en el body (JSON).
3
El backend recibe el request. El servidor de Node.js (o Python, etc.) recibe el POST. Valida que vengan email y password. Si falta alguno, devuelve 400 Bad Request.
4
El backend consulta la base de datos. Hace una query SQL: SELECT * FROM usuarios WHERE email = 'hernan@gmail.com'. La base de datos busca y devuelve el registro si existe.
5
El backend verifica la password. Compara la password ingresada con el hash guardado en la base de datos. Si no coincide, devuelve 401 Unauthorized.
6
El backend genera un token y responde. Si todo está bien, genera un JWT (JSON Web Token) y envía un 200 OK con el token.
7
El frontend recibe la respuesta. Guarda el token (en memoria o localStorage) y redirige al usuario a la pantalla principal.

El Request y Response de login en código

Esto es exactamente lo que viaja por la red en el ciclo que acabamos de ver:

El frontend envía este Request 
POST /api/login HTTP/1.1
Host: api.miapp.com
Content-Type: application/json

{
  "email": "hernan@gmail.com",
  "password": "miPassword123"
}
El backend responde — caso exitoso 
HTTP/1.1 200 OK
Content-Type: application/json

{
  "success": true,
  "mensaje": "Bienvenido, Hernan",
  "token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "usuario": {
    "id": 42,
    "nombre": "Hernan",
    "email": "hernan@gmail.com"
  }
}
El backend responde — password incorrecta 
HTTP/1.1 401 Unauthorized
Content-Type: application/json

{
  "success": false,
  "error": "Email o password incorrectos"
}
🔒
¿Por qué no se dice "password incorrecta"?
Por seguridad, el backend nunca le dice al usuario si el email existe o no. Si dijera "email no registrado", un atacante podría probar emails hasta encontrar uno válido. Por eso siempre se responde: "Email o password incorrectos", sin especificar cuál de los dos falló.

04La Base de Datos: la Memoria de la App

La base de datos guarda toda la información de la app de forma persistente: sobrevive reinicios del servidor, cortes de luz y despliegues nuevos. Sin base de datos, todo se perdería cuando el servidor se apaga.

Cómo se organiza la información: tablas y filas

Una base de datos relacional (como PostgreSQL) organiza los datos en tablas, igual que una hoja de cálculo. Cada tabla tiene columnas (campos) y filas (registros).

Tabla: usuarios

idnombreemailpassword_hashcreado_en
1Maríamaria@mail.com$2b$10$abc...2024-01-10
2Hernánhernan@gmail.com$2b$10$xyz...2024-01-15
3Sofíasofia@mail.com$2b$10$mno...2024-01-20
🔑
Las passwords nunca se guardan en texto plano.
Si la base de datos se filtra, los atacantes no deben poder leer las passwords. Por eso se guardan como un hash — una transformación irreversible. bcrypt es la librería más usada para esto en Node.js. El hash $2b$10$abc... no puede convertirse de vuelta a la password original.

Tipos de bases de datos

TipoCómo funcionaEjemplosCuándo usarlo
Relacional (SQL) Tablas con columnas fijas. Relaciones entre tablas. PostgreSQL, MySQL, SQLite Usuarios, pedidos, productos — datos estructurados
No relacional (NoSQL) Documentos JSON, sin esquema fijo. MongoDB, Firebase Contenido variable, datos anidados complejos
En memoria (Cache) Guarda datos en RAM, muy rápido pero temporal. Redis Sesiones, contadores, datos que cambian mucho

05Arquitectura Completa de una App Real

En producción (una app real funcionando en internet) hay más piezas además de las tres capas. Esta es la arquitectura típica de una startup o app moderna:

Usuario
Abre la app desde su celular o navegador.
CDN
Content Delivery Network: entrega el frontend estático (HTML, CSS, JS) desde servidores cercanos al usuario. Muy rápido.
DNS
Traduce "www.miapp.com" a la IP real del servidor. Como una guía telefónica.
Load Balancer
Distribuye el tráfico entre múltiples instancias del backend para que ninguna se sobrecargue.
Backend (API)
Acá vivimos nosotros. Recibe los requests, corre la lógica de negocio, consulta la base de datos y responde.
Base de datos
Guarda toda la información de forma permanente.
Cache (Redis)
Guarda respuestas frecuentes en memoria para no ir a la base de datos en cada request. Hace la app mucho más rápida.
Servicios ext.
Stripe (pagos), SendGrid (emails), Twilio (SMS), S3 (archivos). El backend los llama cuando los necesita.
🎯
En este curso nos enfocamos en el Backend (API) y la Base de Datos. No te preocupes por el resto. CDN, Load Balancer, Redis y servicios externos son conceptos que van a quedar claros solos a medida que avancés. Al final del curso vas a deployar tu propia API con base de datos en la nube.

06Ejercicio Práctico — Analizá Mercado Libre

Vamos a usar el DevTools para ver en vivo cómo una app real separa el frontend del backend. Usamos Mercado Libre porque tiene una API bien visible.

Preparación

1
Abrí mercadolibre.com.ar en tu navegador
2
Presioná F12 para abrir el DevTools
3
Andá a la pestaña Network y activá el filtro Fetch/XHR. Esto muestra solo los requests de datos, no imágenes ni scripts.
4
Recargá la página con F5. Vas a ver cómo se llenan de requests.

Qué buscar y analizar

Buscá el request principal de productos
Debería ser un GET a una URL como /sites/MLA/search?q=.... Hacé clic en él y andá a la pestaña Response. Vas a ver un JSON con todos los productos que aparecen en pantalla.
Encontrá el campo "results"
En el JSON de respuesta, buscá la clave results. Es un array de objetos. Cada objeto es un producto con su id, title, price, thumbnail y más. Eso es exactamente lo que el backend devuelve al frontend.
Fijate cuánto tarda cada request
La columna Time muestra el tiempo de respuesta en milisegundos. Un buen backend responde en menos de 200ms. Si tarda más de 1000ms, algo está mal (o es una consulta compleja).
Buscá un request POST
Agregá un producto al carrito. En ese momento vas a ver un POST en Network. Hacé clic y mirá el Payload: vas a ver el id del producto que se mandó al servidor. El backend lo recibe, verifica que el usuario esté logueado y guarda el carrito en la DB.
💡
Lo que estás viendo es el contrato entre frontend y backend. Ese JSON que devuelve el backend es exactamente lo que el frontend espera. Si el backend cambia la estructura del JSON sin avisarle al equipo de frontend, la app se rompe. Por eso las APIs tienen documentación y se versionan (v1, v2, v3...) cuando hay cambios grandes.
