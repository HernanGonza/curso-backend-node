01Las Tres Capas de una App

Toda aplicación web moderna está dividida en tres capas que se comunican entre sí. Separar las capas permite que equipos distintos trabajen en paralelo y que cada parte se pueda escalar de forma independiente.

CapaQué haceTecnologíasCorre en
FrontendLa pantalla que ve el usuarioReact, HTML, CSSDispositivo del usuario
Backend (API)El cerebro de la app — lógica y reglasNode.js, Python, JavaServidor (la nube)
Base de datosLa memoria permanente — guarda todoPostgreSQL, MongoDBServidor
Arquitectura simplificada 
[Usuario]  →→→  [Frontend]  →→→  [Backend/API]  →→→  [Base de datos]
               React/App       Node.js/Express       PostgreSQL
               (navegador)     (servidor nube)        (servidor nube)
🍽️
La analogía más útil: el Frontend es el salón del restaurante — lo que ves, el menú, los mozos. El Backend es la cocina — donde se prepara la comida con los ingredientes (base de datos). El cliente nunca entra a la cocina: solo hace el pedido y recibe el plato.

02Qué es una API REST

API (Application Programming Interface) es el contrato entre el Frontend y el Backend: define qué URLs existen, qué datos se mandan y qué datos se reciben.

REST es el estilo más usado para diseñar APIs: usa los métodos HTTP (GET, POST, PUT, DELETE) más URLs claras para representar acciones sobre recursos.

Ejemplo: API de una app de tareas

MétodoURL (endpoint)Qué hace
GET/api/tareasDevuelve todas las tareas del usuario
GET/api/tareas/5Devuelve solo la tarea con id = 5
POST/api/tareasCrea una tarea nueva (datos en el body)
PUT/api/tareas/5Reemplaza completamente la tarea 5
PATCH/api/tareas/5Modifica solo algunos campos de la tarea 5
DELETE/api/tareas/5Elimina la tarea 5
💡
La URL representa el recurso, el método representa la acción. /api/tareas es el recurso "tareas". GET sobre ese recurso = leer. POST = crear. La combinación método + URL define completamente qué operación se hace.

03El Ciclo Completo de un Login

Cuando un usuario inicia sesión en cualquier app, pasan exactamente estos 7 pasos. Entender este ciclo es clave para construir cualquier backend con autenticación.

Paso 1 — El usuario completa el formulario: escribe su email y password y hace clic en "Ingresar"
Paso 2 — El frontend envía un POST /api/login con los datos en el body en formato JSON
Paso 3 — El backend recibe el request y valida que lleguen los campos requeridos. Si falta algo → responde 400
Paso 4 — Consulta la base de datos: busca el usuario por email con SQL
Paso 5 — Si el usuario no existe → 401. Si existe, verifica la password contra el hash guardado
Paso 6 (si falla) — Hash no coincide → responde 401: "Email o password incorrectos"
Paso 7 (si sale bien) — Genera un JWT (token), responde 200 con el token y los datos del usuario
HTTP — Request y Response del login 
// El frontend envía:
POST /api/login HTTP/1.1
Content-Type: application/json

{ "email": "hernan@gmail.com", "password": "miPass123" }


// El backend responde si todo OK:
HTTP/1.1 200 OK
Content-Type: application/json

{
  "success": true,
  "token": "eyJhbGciOiJIUzI1NiJ9...",
  "usuario": { "id": 42, "nombre": "Hernan", "rol": "admin" }
}


// El backend responde si la password es incorrecta:
HTTP/1.1 401 Unauthorized
Content-Type: application/json

{ "success": false, "error": "Email o password incorrectos" }
🔒
Seguridad clave: el backend nunca dice cuál de los dos falló — ni "el email no existe" ni "la password es incorrecta". Siempre el mensaje genérico: "Email o password incorrectos". Si dijera cuál, un atacante podría probar emails hasta encontrar uno válido en el sistema.

04La Base de Datos

La base de datos guarda la información de forma persistente: sobrevive reinicios del servidor, cortes de luz y actualizaciones del código. Sin base de datos, todo se perdería al apagar.

Ejemplo de tabla usuarios en PostgreSQL

idnombreemailpassword_hashrolcreado_en
1Maríamaria@mail.com$2b$10$abc...admin2024-01-10
2Hernánhernan@gmail.com$2b$10$xyz...viewer2024-01-15
🔑
Las passwords NUNCA se guardan en texto plano.
Se guardan como un hash irreversible generado con bcrypt. El hash $2b$10$abc... no puede convertirse de vuelta a la password original — ni el propio servidor la conoce.

Cuando el usuario inicia sesión, bcrypt compara la password ingresada contra el hash guardado. Si coinciden → acceso. Si no → 401. Nunca se desencripta nada.

Tipos de base de datos

TipoEjemplosCuándo usarlo
SQL / RelacionalPostgreSQL, MySQLDatos estructurados con relaciones entre tablas. El estándar para la mayoría de las apps.
NoSQLMongoDB, FirebaseDocumentos JSON flexibles, estructuras que cambian mucho.
Cache (en memoria)RedisDatos en RAM: muy rápido pero temporal. Ideal para sesiones y datos frecuentes.
✓
En este curso usamos PostgreSQL — es el más usado en el mundo para backends profesionales, es open source y las plataformas de deploy lo incluyen gratis.

05Arquitectura en Producción

Una app real en producción tiene más piezas que solo el backend y la base de datos. Acá está el panorama completo:

Usuario
Abre la app desde su celular o navegador.
DNS
Traduce "www.miapp.com" a la IP real del servidor. Es como la guía telefónica de internet.
CDN
Entrega el frontend estático (HTML, CSS, imágenes) desde servidores cerca del usuario. Muy rápido.
Load Balancer
Distribuye el tráfico entre múltiples instancias del backend para no saturar ninguna.
Backend (API)
Recibe los requests, corre la lógica de negocio y consulta la base de datos. Acá vivimos nosotros.
Base de datos
PostgreSQL: guarda toda la información de forma permanente.
Cache (Redis)
Guarda respuestas frecuentes en memoria RAM. El backend la consulta antes de ir a la DB — mucho más rápido.
Servicios ext.
Stripe (pagos), SendGrid (emails), S3 (archivos). El backend los llama cuando los necesita.
🎯
En este curso nos enfocamos en el Backend y la Base de datos. Al terminar vas a poder construir y deployar una API completa en Render o Railway. El Load Balancer, CDN y Redis los vas a conocer cuando el proyecto escale.

06Ejercicio — Analizar Mercado Libre

Vamos a ver en vivo cómo el backend de Mercado Libre responde a los requests del frontend.

🔍
Paso a paso:
1) Abrí mercadolibre.com.ar → F12 → pestaña Network → filtro Fetch/XHR → recargá con F5
2) Hacé clic en el primer request largo (suele tener una URL con /search o /recommendations)
3) Pestaña Headers: mirá el método (GET), la URL completa y el status code (200)
4) Pestaña Response: expandí el campo results — ahí están los productos
5) Expandí un resultado: vas a ver id, title, price, thumbnail
6) Eso es exactamente lo que el backend de ML le manda al frontend
🔥
Desafío:
• Agregá un producto al carrito y buscá el POST que aparece → pestaña Payload para ver qué datos manda el frontend
• Buscá un request que tenga el header Authorization — eso significa que el usuario está logueado
• Fijate en la columna Time: ¿cuántos milisegundos tarda en responder el backend de ML?
💡
Lo que ves en la pestaña Response es el JSON crudo que genera el backend. El frontend agarra ese JSON y lo convierte en la pantalla de productos que ves. Al final de este curso vas a poder construir algo equivalente.
