Conexión Node + PostgreSQL

Conectá tu servidor Express a una base de datos PostgreSQL real con node-postgres, manejá credenciales con dotenv, y escribí queries seguras con parámetros. Cierra el Bloque 6.

60 minutos Requiere Clase 27
Objetivos de la clase
  • Comprender por qué Node.js necesita un paquete driver para poder comunicarse con PostgreSQL.
  • Instalar y configurar node-postgres (pg) en un proyecto Express.
  • Utilizar dotenv para mantener las credenciales de la base de datos fuera del código fuente.
  • Crear y entender un Pool de conexiones hacia PostgreSQL.
  • Ejecutar la primera consulta SQL real desde código Node.js.
  • Escribir queries con parámetros para prevenir SQL Injection al recibir datos del usuario.

01¿Por Qué Node.js Necesita un Driver?

Hasta ahora ejecutamos SQL directamente en pgAdmin o en VS Code, escribiendo las sentencias a mano. Pero el objetivo final es que sea nuestro servidor Express el que hable con PostgreSQL: cuando llega un GET a /productos, el controller tiene que consultar la base de datos real y devolver esos resultados, en lugar del array en memoria que usamos en el Bloque 5.

Node.js no sabe, por sí solo, cómo comunicarse con PostgreSQL: son dos programas completamente distintos, escritos en tecnologías diferentes. Para que puedan conversar, se necesita un driver: una librería que traduce el código JavaScript en el protocolo de comunicación específico que entiende PostgreSQL.

💡
Analogía práctica: Es como dos personas que hablan idiomas distintos y necesitan un traductor para entenderse. node-postgres es exactamente ese traductor entre el JavaScript de tu servidor y el motor de PostgreSQL.

02Instalando node-postgres (pg)

node-postgres, distribuido bajo el nombre de paquete pg, es el driver oficial y más utilizado para conectar Node.js con PostgreSQL. Se instala como cualquier otra dependencia del proyecto.

bash
npm install pg

A diferencia de nodemon, pg es una dependencia de producción: la aplicación la necesita para funcionar en cualquier entorno, no solo durante el desarrollo.

03dotenv: Variables de Entorno para las Credenciales

Para conectarse a PostgreSQL, la aplicación necesita datos sensibles: usuario, contraseña, nombre de la base de datos, host y puerto. Escribir esos valores directamente en el código ("hardcodeados") es una mala práctica grave: si el código se sube a un repositorio público, esas credenciales quedan expuestas para cualquiera.

bash
npm install dotenv

El paquete dotenv permite guardar esos valores en un archivo separado llamado .env, que nunca se sube al repositorio (se agrega a .gitignore), y cargarlos como variables de entorno accesibles desde process.env.

bash
# .env
DB_USER=postgres
DB_PASSWORD=tu_contrasena
DB_HOST=localhost
DB_PORT=5432
DB_NAME=tienda_virtual
javascript
// index.js - al principio de todo, antes de usar process.env
require('dotenv').config();
⚠️
Nunca subir el .env: El archivo .env debe estar listado en .gitignore desde el primer commit del proyecto. Si ya se subió por error alguna vez, cambiar la contraseña real de la base de datos es la única forma segura de resolverlo.

04Creando el Pool de Conexiones

Un Pool es un conjunto de conexiones reutilizables hacia la base de datos, administradas automáticamente por pg. En lugar de abrir y cerrar una conexión nueva por cada consulta (una operación relativamente costosa), el Pool mantiene varias conexiones abiertas y las reparte entre las distintas queries que van llegando.

javascript
// db.js
require('dotenv').config();
const { Pool } = require('pg');

const pool = new Pool({
  user: process.env.DB_USER,
  password: process.env.DB_PASSWORD,
  host: process.env.DB_HOST,
  port: process.env.DB_PORT,
  database: process.env.DB_NAME,
});

module.exports = pool;
🛡️
Por qué se centraliza en db.js: Crear el Pool una única vez, en su propio archivo, y exportarlo, permite que cualquier controller del proyecto lo importe y lo reutilice, en vez de crear una conexión nueva en cada archivo.

05Ejecutando la Primera Query desde Node

El Pool expone un método query(), que recibe una sentencia SQL como string y devuelve una promesa. Como ya se practicó con fetch y las funciones asíncronas del Bloque 5, se puede resolver con async/await.

javascript
// controllers/productos.controller.js
const pool = require('../db');

exports.obtenerTodos = async (req, res) => {
  try {
    const resultado = await pool.query('SELECT * FROM productos');
    res.json(resultado.rows);
  } catch (error) {
    res.status(500).json({ error: 'Error al consultar productos' });
  }
};

El objeto que devuelve pool.query() trae varias propiedades; la más usada con diferencia es rows, que contiene un array con las filas del resultado, ya convertidas en objetos JavaScript listos para usar con res.json().

06Queries con Parámetros: Previniendo SQL Injection

Cuando una query necesita incorporar un valor dinámico —por ejemplo, un id que llega por req.params— nunca se debe concatenar ese valor directamente dentro del string SQL. Hacerlo abre la puerta a un ataque conocido como SQL Injection, donde alguien malintencionado inyecta código SQL propio disfrazado de un parámetro normal.

javascript
// (X) PELIGROSO: nunca concatenar directamente
const id = req.params.id;
const resultado = await pool.query(`SELECT * FROM productos WHERE id = ${id}`);

// (OK) CORRECTO: query parametrizada, con $1 como placeholder
const resultado = await pool.query(
  'SELECT * FROM productos WHERE id = $1',
  [id]
);

El símbolo $1 es un marcador de posición: pg se encarga de insertar el valor de forma segura, escapando cualquier carácter que pudiera alterar la estructura de la consulta. Con varios parámetros, se numeran en orden: $1, $2, $3, etc.

javascript
exports.crear = async (req, res) => {
  const { nombre, precio } = req.body;
  const resultado = await pool.query(
    'INSERT INTO productos (nombre, precio) VALUES ($1, $2) RETURNING *',
    [nombre, precio]
  );
  res.status(201).json(resultado.rows[0]);
};
⚠️
Sobre RETURNING *: Agregar RETURNING * al final de un INSERT le pide a PostgreSQL que devuelva la fila recién creada (con su id ya generado por SERIAL) en el mismo resultado, evitando tener que hacer una segunda consulta para obtenerla.
